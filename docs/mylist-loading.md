# 本人用マイリストの読み込み改善

`mylist.html#mine` の表示と共有同期は、同じアカウントの `list-master-cache.js` を共用します。同一曲の進行中の取得も共有するため、別々に読み込む重複を防ぎます。公開マイリストの読み取り・公開停止の判定は従来どおりFirebaseに従います。

端末のIndexedDB `share-list-score-mylist-master-v1` には、アカウントごとに公開楽曲のタイトル・アーティスト・ChordWiki URL・ジャンルだけを保存します。Key、担当パート、登録フラグ、表示名、メールアドレス、共有用トークン、背景画像、認証情報は保存しません。最大2MB、有効期間7日です。ストレージが利用できない場合は通常の取得を続けます。

本人の登録曲・Key・パート・表示設定は毎回Firebaseで確認します。前回の楽曲情報が揃っている場合は、それらの最新の本人設定と組み合わせて表示し、マスターのリビジョンを確認して更新します。共有データの公開処理には、リビジョン確認済みの楽曲情報を使います。背景画像の読み込みは一覧の初回表示を待たせません。

マスターのリビジョン更新・管理者の全体キャッシュ削除で取得済みデータを無効にします。本体の管理者指示処理も新しいキャッシュを削除します。同じ指示が別タブの通知とFirebaseの両方から届いても重複処理を避けます。ログアウト・アカウント変更時は前のアカウントのキャッシュと購読を破棄し、古い処理結果を表示へ戻しません。Firebase上の保存済みマイリストは削除しません。

検証は合成データ205曲を使用しました。表示100行＋共有有効の場合、楽曲取得APIの呼び出しは従来410回から初回205回、端末キャッシュとリビジョンが有効な再読み込みでは0回でした。これはアプリ内の取得呼び出し回数であり、本番の通信時間や実際のHTTPリクエスト数の計測ではありません。Firebase認証・本人データ確認・共有同期の通信は引き続き発生します。

回帰検証ではUI編集、URLコピー、公開停止・再開、共有URLの維持、お気に入り、Key変更、曲の削除、PC・スマホ・タブレット幅を確認しました。`node scripts/check-list-master-cache.cjs` で重複取得、失敗後の再試行、リビジョン・管理者指示の無効化、アカウント分離、ログアウト中の処理中止、ストレージ拒否時の動作を検証します。
